# Разбор tlroadmap.io — что берём, что не берём

**Что это:** одностраничный конспект исследования [tlroadmap.io](https://tlroadmap.io/) — известной русскоязычной карты компетенций для тимлида (авторы: Stas Tsyganov, Egor Tolstoy & community; CC BY-SA 4.0; несколько тысяч человек-валидаторов). Цель — выделить, что в их подходе работает и применимо у нас, а что мы намеренно делаем иначе.

Документ — рабочий артефакт inventory; на сайт не публикуется, живёт в репозитории.

## Их структура и наш контраст

| Аспект | tlroadmap.io | The-Way-of-SRE |
| ------ | ------------ | -------------- |
| Top-level model | **Role-based**: Administrator / Integrator / People Manager / Product Owner / Technical Lead + Personal Skills | **Domain-based**: Culture / Engineering / Practices |
| Глубина | До 4+ уровней (TechLead → Product Quality → Testing → Test Pyramid → Unit Testing) | 3 уровня (Branch → L1 → Leaf), leaf — конечный узел |
| Visualization | Clickable image (общая схема) + текстовое sidebar-меню | Inline SVG Spider + Starlight sidebar |
| Priority markers | **Нет** (must/should/could / junior-senior отсутствуют) | Must Have / Mandatory / Nice to have / On Demand (🔴🟡🟢🔵) |
| Level markers | **Нет** | SFIA-уровни (L3 / L4 / L5 / L6+) для каждой формулировки |
| Progress tracking | Нет | Нет |
| Лицензия | CC BY-SA 4.0 | Apache 2.0 |
| Контрибуция | Открытая PR-based, явный `/contributing` гайд | Открытая PR-based |

## Структура их leaf-страницы (пример: Unit Testing)

1. **Описание** — что это.
2. **Почему ветка важна?** — мотивация.
3. **Что будет, если её не делать?** — последствия отсутствия.
4. **На кого может быть делегирована?** — кому передать, если сам не готов.
5. **Примеры поведения** — пары good / bad для конкретных ситуаций.
6. **Способы прокачки** — конкретные действия для роста (не только материалы для чтения).
7. **Консультации** — кого спросить (имена, каналы внутри сообщества).
8. **Теория** — фундаментальные утверждения (например, шесть свойств unit-теста).

## Структура нашего leaf-шаблона

Lead-параграф (1–2 предложения, граница концепта) → `:::note` метаданные (ветвь, путь, SFIA, приоритет, статус) → **Что должен уметь** (по SFIA-уровням) → **Материалы** (книги / статьи / курсы / инструменты) → **Best practices** (правило + антипаттерн в одном пункте) → **Связанные листья** (с типом связи: предпосылка / продолжение / альтернатива) → **Открытые вопросы**.

## Что у них **берём**

Несколько секций tlroadmap явно сильнее нашего шаблона и стоит подумать о их интеграции:

1. **«Почему важна?» как явный раздел.** У нас мотивация компетенции размазана по lead-параграфу. Явный «почему» раздел упрощает быстрое сканирование и даёт читателю основу для решения «учить или пропустить». Не обязательно отдельная секция в шаблоне; можно усилить lead, добавив явную мотивационную часть.
2. **«Что будет, если её не делать?» — последствия отсутствия.** Это motivation pattern, который у нас отчасти отражён через best practices с антипаттернами, но не как явный сценарий «организация без этой компетенции». Сильный приём для убеждения скептиков и руководства; рассмотреть как опциональный блок в шаблоне для листьев, где это применимо (Postmortem Culture, Runbooks, SLO Engineering — где «не делать» = известный класс инцидентов).
3. **«Способы прокачки» как конкретные действия, а не только материалы для чтения.** У нас «должен уметь» формулирует целевое состояние, «Материалы» дают reference, но **между ними gap**: как именно дойти от «знаю что должен» до «умею». Способы прокачки tlroadmap: pair-программирование, code review соседних команд, ведение собственного проекта, обучение младших, written summary прочитанного. Это deliberate practice уровень.

## Что у них **не берём** (с обоснованием)

1. **Role-based модель (Administrator / Integrator / PM / PO / TechLead).** SRE — это специфическая роль с собственной техникой и культурой; разбиение на под-роли создаёт ложную фрагментацию (SRE одновременно немного админ, немного PO, немного TechLead). Domain-based (Culture / Engineering / Practices) точнее отражает, что SRE — это **набор компетенций**, не **набор подролей**.
2. **Личные навыки (Communications / Management / Self-Development) как отдельный трек.** Эти темы для SRE менее центральны, чем для тимлида, и частично покрыты через `Dev Team Partnership` и `Organisational Capability Development`. Отдельный трек размывает фокус roadmap на SRE-специфике.
3. **«Делегирование» как раздел.** Для тимлида делегирование — основная активность («это нужно делать, но не обязательно мне»). Для SRE-инженера делегирование — другой паттерн: SRE не передаёт компетенцию, а **владеет** ею или **переносит обратно в dev-команду через partnership** (см. `Dev Team Partnership`, exit-критерий engagement). Имеет смысл скорее как часть `Service Ownership` / `Dev Team Partnership`, а не как универсальный раздел шаблона.
4. **«Консультации» (имена и каналы).** Привязка к конкретным людям делает документ хрупким (люди уходят, контакты устаревают). У нас вместо этого — ссылки на канонические внешние источники (книги, доклады, документация); консультации внутри организации — отдельная компетенция (`SRE Onboarding` → mentor рассматривает это).
5. **Глубина 4+ уровней (Branch → L1 → L2 → L3 → Leaf).** У нас более плоская иерархия (3 уровня), и leaf — единица описания одной практики. Глубже уходить ценнее, когда таксономия очень разветвлённая (как у тимлида); для SRE 3 уровней достаточно — глубокая иерархия делает навигацию тяжелее.

## Открытые вопросы / возможные эксперименты

- **Эксперимент: расширить `_template.md` опциональным разделом «Что будет, если не делать».** Для листьев, где есть очевидный negative scenario (Postmortem Culture без blameless → blame culture → churn; Runbooks без них → высокий MTTR + alert fatigue; SLO Engineering без него → reliability как «по ощущениям»). Не обязательный, не для каждого листа — но как опция мощно усиливает мотивационную часть.
- **Эксперимент: добавить раздел «Способы прокачки» как отдельный шаг между «Что должен уметь» и «Материалы».** Конкретные действия: pair on-call, проведение wheel of misfortune, написание SLI для соседнего сервиса, ведение incident log одного дежурства подряд. Не reading list, не цель — а deliberate practice.
- **Эксперимент: переписать lead-параграф нескольких листьев с явным «зачем».** Сейчас lead описывает концепт; в формулировке tlroadmap'а — концепт + мотивация одной фразой («без неё через год команда теряет / получает / не может»).
- Обновления `_template.md` под результаты этих экспериментов — отдельным PR, после проведения эксперимента на одном-двух листьях.

Защита целостности **всей** software supply chain — от source code и build-системы до distribution и runtime verification. Четвёртый лист под L1 `Information Security`, сосед к [Vulnerability Management](/The-Way-of-SRE/leaves/practices/vulnerability-management/), [Secrets Management](/The-Way-of-SRE/leaves/practices/secrets-management/) и [Threat Modeling](/The-Way-of-SRE/leaves/practices/threat-modeling/). **Граница с Vulnerability Management чёткая**: VM реагирует на known CVE в коде и dependencies — что уже сломано; Supply Chain Security защищает сам процесс build → sign → distribute → verify от компрометации — где будущая уязвимость не успеет стать известной CVE, а попадёт в прод через скомпрометированный pipeline. Не «scanner и галочка» — контролируемая цепочка артефактов с криптографически проверяемым **provenance**. SolarWinds (2020), Codecov (2021), 3CX (2023), xz-utils (2024), и десятки typosquatting / dependency confusion инцидентов в npm/PyPI показали, что атака смещается с runtime на build- и distribution-слои. SLSA как фреймворк уровней зрелости, Sigstore как практическая реализация signing/verification, SBOM как ledger того, что реально в артефакте.

## Что должен уметь

- **L4** — Понимает scope `software supply chain` — это не только OSS dependencies, а **вся** цепочка: source repository → build runner → artifact registry → deployment → runtime. Каждое звено имеет threat surface (compromised maintainer, malicious build step, registry poisoning, tampered artifact in transit).
- **L4** — Применяет **signed commits** (GPG / Sigstore gitsign) и **branch protection** (signed-only merge в protected branches). Понимает, что unsigned commit от верифицированной identity ≠ verified commit; branch protection rules — первая граница против compromised developer account.
- **L4** — Внедряет **Pipeline-as-Code в репо** (не в UI), все CI/CD secrets через **OIDC federation** (короткоживущие токены), а не long-lived PATs. Runners — ephemeral (не self-hosted persistent), build steps — pinned by digest (`@sha256:...`), не by mutable tag.
- **L5** — Проектирует **SLSA-compliant pipeline** — выбирает target level (1–4) по compliance/criticality. SLSA Level 2 (provenance generated, hosted build) — достижимый baseline; Level 3 (provenance non-forgeable, isolated build) — для production-critical артефактов; Level 4 (hermetic, two-party review) — для regulated industries.
- **L5** — Генерирует и публикует **SBOM** (Software Bill of Materials) — SPDX или CycloneDX format, генерация в CI/CD каждого артефакта (Syft / cdxgen), attestation подписан, доступен через registry или public endpoint. Понимает разницу `build-time SBOM` (что собралось) и `runtime SBOM` (что фактически загружено в memory) — для эксплуатируемых vulnerabilities matter второе.
- **L5** — Применяет **artifact signing & verification** — Sigstore cosign для container images и release artifacts, keyless signing через OIDC (короткоживущие certificates, Rekor transparency log), admission policies в k8s (Cosign Policy Controller / Kyverno / Connaisseur) для verify-on-deploy. Не «подписали и забыли» — verification в deploy-time блокирует unsigned/untrusted артефакты.
- **L5** — Защищается от **dependency confusion и typosquatting** — internal packages с reserved namespace в public registry (либо явные scope/prefix), strict resolver config (no fallback от private к public registry), allow-list maintained internal-mirror для critical dependencies. Coordinates с Vulnerability Management по dependency hygiene (cool-off period, maintained status).
- **L6+** — Внедряет **org-level supply chain security program** — SLSA roadmap по сервисам (compliance, criticality buckets), centralized signing infrastructure (Sigstore self-hosted Fulcio + Rekor либо HashiCorp Vault as KMS), policy-as-code для verification (OPA / Kyverno), vendor security assessment process (третья сторона = часть supply chain), regulatory mapping (EO 14028, EU CRA, NIST SSDF).
- **L6+** — Принимает strategic decisions — build-vs-buy для critical OSS dependencies (внутренний форк vs upstream contribution vs vendor support contract), insurance implications (cyber insurance требует proof of supply chain controls), incident response планирование под supply chain compromise (revoke-and-rotate scope — keys, tokens, artifacts), участие в OSS security инициативах (OpenSSF Scorecard, Allstar, Sigstore upstream).

## Материалы

### Книги и фреймворки

- **[SLSA — Supply-chain Levels for Software Artifacts](https://slsa.dev/)** (OpenSSF). **База.** Канонический фреймворк уровней зрелости supply chain security (levels 1–4). Specs по build, source, dependencies. Maintained OpenSSF, реализуется в GitHub Actions, GitLab, BuildKit и других системах.
- **[The Update Framework (TUF)](https://theupdateframework.io/)** (CNCF graduated). **База.** Спецификация secure software update systems — устойчива к key compromise, registry compromise, replay attacks. Используется как foundation в Sigstore, Notary v2, Datadog Agent. Long-form spec — для глубокого понимания threat model.
- **[in-toto framework](https://in-toto.io/)**. **Дополнительно.** Спецификация attestation цепочки supply chain (кто что делал в pipeline). SLSA использует in-toto attestations как формат. Полезно понимать формат, если генерируешь custom attestations.
- **[NIST SSDF (Secure Software Development Framework) SP 800-218](https://csrc.nist.gov/Projects/ssdf)**. **База для compliance.** US federal требования к software vendors после EO 14028 — обязательны для federal procurement. Self-attestation form на основе SSDF.

### Статьи и доклады

- **[Reproducible Builds](https://reproducible-builds.org/)**. **База.** Movement и tooling за bit-for-bit reproducibility — основа для verifiable build attestations. Debian / NixOS / Bazel — practical implementations.
- **[Google — Building Secure and Reliable Systems, chapter on Software Supply Chain](https://google.github.io/building-secure-and-reliable-systems/raw/ch14.html)** (O'Reilly, 2020). **Дополнительно.** Google-perspective на supply chain (BCID, Borg-based deployment verification, internal Sigstore lineage).
- **[The SolarWinds Cyberattack — CISA report](https://www.cisa.gov/news-events/news/remediating-networks-affected-solarwinds-and-active-directory-m365-compromise)**. **База.** Канонический watershed-инцидент supply chain compromise — атакующие вошли через build system и подписали malicious update легитимным cert. Читать для понимания почему build environment integrity критично.
- **[The xz-utils backdoor (CVE-2024-3094) — Andres Freund's discovery thread](https://www.openwall.com/lists/oss-security/2024/03/29/4)**. **База.** Свежайший case study (март 2024) social engineering атаки на single-maintainer critical OSS project через многолетнее построение доверия. Урок: dependency hygiene + maintained status + multi-maintainer requirements.
- **[Codecov Bash Uploader Compromise — Codecov post-mortem](https://about.codecov.io/security-update/)**. **Дополнительно.** Build pipeline compromise через подменённый Docker image; secrets из CI клиентов утекли. Урок: pinned digests, verify before use, no curl-pipe-bash в pipeline.
- **[The State of the Software Supply Chain](https://www.sonatype.com/state-of-the-software-supply-chain/introduction)** (Sonatype, ежегодно). **Дополнительно.** Индустриальные данные о растущих malicious packages, time-to-fix metrics, OSS health indicators.
- **[OpenSSF Scorecard](https://github.com/ossf/scorecard)**. **База.** Automated assessment OSS репозиториев по security practices (signed releases, branch protection, dependency updates, CI tests, fuzzing). Полезно для evaluation upstream dependencies.

## Best practices

- **Signed commits + signed releases — обязательная база, не «когда дойдут руки».** Антипаттерн: «у нас branch protection, этого хватает». Branch protection защищает от случайного push в master, не от compromised developer credentials. Signed commits (GPG / SSH / Sigstore gitsign) с verification в branch protection rules — первая защита от credential theft. Signed releases (cosign / GPG) — гарантия consumers, что артефакт собран legitimate process. Cost внедрения — низкий (один раз настроить per-developer + CI), value — protection from a class of incidents в принципе.
- **Pin everything by digest, not by tag.** Антипаттерн: `FROM node:18`, `uses: actions/checkout@v4`, `pip install foo==1.2.3` без hash. Tags mutable — можно опубликовать malicious image с тем же tag. Digest immutable — `FROM node@sha256:abc...`, `uses: actions/checkout@8e5e7e5...` (commit SHA или digest), `pip install --require-hashes`. Renovate / Dependabot обновляют digests automatically. Cost — нулевой после automation; protection — большой против compromised registries и intentional malicious updates.
- **Build environment как threat surface — ephemeral runners, OIDC federation, no long-lived secrets.** Антипаттерн: self-hosted persistent runner с long-lived PAT в env. Persistent runner — атакующий получает доступ ко всем последующим builds. OIDC federation выдаёт короткоживущий token per-workflow (15 min lifetime), привязанный к specific repo/branch/workflow — украденный token бесполезен для другого pipeline. Ephemeral runners (GitHub-hosted, или self-hosted с clean state per job) — каждый build starts от clean slate.
- **SBOM как foundational artifact — генерируется per-build, attested, archived.** Антипаттерн: «SBOM сгенерируем когда compliance аудит попросит». Без historical SBOM невозможно ответить «в какой версии артефакта был vulnerable package» — критично для incident response при обнаружении CVE через 6 месяцев после релиза. SBOM генерируется в CI/CD как artifact каждого build (Syft / cdxgen), attached к release, archived с retention ≥1 год. Format — SPDX (ISO standard) или CycloneDX (богаче на metadata, OWASP). Чтобы было полезно для consumers — published в registry или public endpoint.
- **Verify-on-deploy, не verify-on-build.** Антипаттерн: «мы подписали в CI, дальше доверяем». Между build и deploy артефакт может быть подменён (registry compromise, MITM, supply chain attack downstream). Admission controllers (Cosign Policy Controller / Kyverno / Connaisseur) проверяют signature **в момент deploy** в k8s — unsigned/untrusted image не запустится. Aналогично для package managers — verify hash при install (pip `--require-hashes`, npm `--integrity`). Trust boundary — deploy time, не build time.
- **Dependency confusion — реальный риск, защита через namespace reservation.** Антипаттерн: internal package `mycompany-utils` существует только во внутреннем registry, public registry не проверяется. Атакующий публикует `mycompany-utils@99.0.0` в public npm/PyPI; resolver с fallback к public берёт его (higher version wins). Защита: scope в public registry (`@mycompany/utils` зарезервирован, либо публикуется stub), strict resolver config (`registry=https://internal/`, no public fallback), либо allow-list через internal-mirror (Verdaccio / pypi-mirror / Nexus) с manual approval для new deps. Atlassian / Microsoft / Yelp писали о реальных инцидентах в 2021.
- **Reproducible builds где практично, attestation everywhere.** Антипаттерн: «у нас artisanal builds, каждый build уникален — но мы их подписываем». Reproducible build (bit-for-bit identical output из same input) — gold standard, но дорогой для C/C++/system languages. Где недостижимо — генерируется in-toto attestation (кто, когда, какими tools, из каких inputs). Verification = either reproduce-and-compare, либо trust the attestation chain. SLSA Level 3 требует non-forgeable provenance (attestation подписан isolated build service), Level 4 требует hermetic + two-party review.

## Связанные листья

- **[Vulnerability Management](/The-Way-of-SRE/leaves/practices/vulnerability-management/)** — граница: VM = реагирует на known CVE в коде/dependencies (что уже сломано); Supply Chain Security = защищает процесс build → sign → distribute → verify (где будущая уязвимость не успеет стать CVE). Оба используют SBOM как foundation — но для разных целей: VM ищет vulnerable packages в SBOM, Supply Chain Security гарантирует, что SBOM достоверен.
- **[Secrets Management](/The-Way-of-SRE/leaves/practices/secrets-management/)** — пересечение в OIDC federation (короткоживущие tokens вместо long-lived) и signing keys management. Centralized signing infrastructure (Fulcio / KMS) — это secrets-management discipline применённая к signing keys.
- **[Threat Modeling](/The-Way-of-SRE/leaves/practices/threat-modeling/)** — supply chain — один из trust boundaries в DFD. Threat modeling SLSA Level выбирается с учётом threat model сервиса (что мы защищаем, от кого, какой acceptable level).
- **[CI/CD](/The-Way-of-SRE/leaves/engineering/ci-cd/)** — pipeline и есть основной surface для supply chain compromise. Pipeline-as-Code, ephemeral runners, OIDC federation, signed artifacts — пересекаются с CI/CD best practices. SLSA Level 2+ требует hosted build service (GitHub Actions / GitLab CI / Cloud Build) — нельзя на laptop.
- **[Progressive Delivery](/The-Way-of-SRE/leaves/practices/progressive-delivery/)** — verify-on-deploy admission policies встроены в deployment pipeline (canary с health gate + signature verification как обязательный pre-condition).
- **[Infrastructure as Code](/The-Way-of-SRE/leaves/engineering/infrastructure-as-code/)** — Terraform modules / Helm charts / Ansible roles тоже supply chain. Аналогичные практики: signed releases, pinned versions, SBOM (для IaC меньше развит, но появляется).
- **[Incident Response](/The-Way-of-SRE/leaves/practices/incident-response/)** — supply chain compromise — особый класс инцидентов: blast radius может быть огромный (все consumers за время от compromise до detection), remediation требует revoke-and-rotate scope (keys, tokens, artifacts, downstream notification).

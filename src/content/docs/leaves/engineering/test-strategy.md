Дисциплина **проектирования testing portfolio** под характеристики системы — что тестируется, на каком уровне (unit / integration / contract / e2e), с какой стоимостью поддержки и какой полнотой сигнала о regressions. Третий лист под L1 `Programming / Scripting`, сосед к [Programming Languages](/The-Way-of-SRE/leaves/engineering/programming-languages/) и [CI/CD](/The-Way-of-SRE/leaves/engineering/ci-cd/). Не «code coverage 80%», не «у нас написаны тесты» — а архитектура testing portfolio: test pyramid как baseline (Mike Cohn 2009, актуален и сейчас), contract testing как сшивка распределённых сервисов (Pact, Spring Cloud Contract), flake management как первоклассная operational забота (`flaky test` ломает trust в CI быстрее, чем reliability сервиса), coverage и mutation как метрики (а не как цель — Goodhart's law). Тесты — **пре-условие** CI/CD и progressive delivery (зелёный pipeline должен значить, что артефакт безопасно катить), не «когда дойдут руки до автоматизации».

## Что должен уметь

- **L3** — Пишет unit-тесты для своего кода (фокус — public API, не private internals), понимает разницу `unit` vs `integration` vs `e2e`. Не путает test pyramid (много дешёвых unit, мало дорогих e2e) с ice cream cone (много e2e, мало unit — медленно и хрупко).
- **L3** — Применяет table-driven tests / property-based testing для покрытия input space, не пишет N однотипных копий с разными константами. В Go — `t.Run` с table; в Python — `pytest.mark.parametrize`; в Rust — `proptest` или аналог.
- **L4** — Проектирует testing portfolio для сервиса — какие layers (unit / integration / contract / e2e), какие dependencies реальные vs замокированные, где живут integration-тесты (in-process testcontainers vs shared staging vs ephemeral env). Понимает, что shared staging — антипаттерн для test isolation.
- **L4** — Применяет **contract testing** между сервисами (Pact / Spring Cloud Contract / Hoverfly) — consumer-driven contracts проверяются обеими сторонами в CI. Понимает, зачем contract testing нужен в дополнение к unit и e2e: даёт fast feedback на breaking changes в API без поднятия всего стека.
- **L4** — Управляет **flaky tests** как operational зачем — измеряет flake rate, изолирует / quarantine'ит flaky tests, докладывает root cause не «retry'ем покрыли». Понимает, что 5% flake rate в pipeline = 100% trust loss в CI: разработчики перестают верить failed build и сразу нажимают retry, прячут реальные regressions.
- **L5** — Проектирует **test data strategy** — fixtures vs factories vs builders vs golden data sets; persistent test DB vs ephemeral per-test; PII / GDPR considerations для test data (нельзя dump prod в staging без масштабной анонимизации). Решает trade-off realistic data (полнота сигнала) vs deterministic test (стабильность).
- **L5** — Внедряет **mutation testing** как метрику качества test suite (Pitest / Stryker / Cosmic Ray / `go-mutesting`). Понимает разницу line coverage (что код выполнился) и mutation score (что тесты ловят bugs). Coverage 90% при mutation score 30% = тесты пишут историю без assertions.
- **L5** — Проектирует **non-functional testing** — performance / load / stress / soak / chaos как отдельные категории, со своими environments, baselines и acceptance criteria. Performance regression test в CI — отдельная история от correctness test. Граница к [Chaos Engineering](/The-Way-of-SRE/leaves/engineering/chaos-engineering/): chaos = hypothesis-driven experiments в проде/preprod; load test = известная forcing function в staging.
- **L6+** — Внедряет org-level testing standards — minimum bar (coverage / mutation thresholds per criticality bucket), CI gates (что blocking, что warning), shared test infrastructure (Pact broker / contract registry, ephemeral env factory, test data services), test ownership и maintenance ritual (broken / flaky tests как technical debt с SLA). Принимает strategic decisions о build-vs-buy для test infrastructure (Cypress Cloud vs self-hosted Selenium grid; Pact Broker SaaS vs hosted).

## Материалы

### Книги

- Kent Beck — **[Test-Driven Development: By Example](https://www.amazon.com/Test-Driven-Development-Kent-Beck/dp/0321146530)** (Addison-Wesley, 2002). **База.** Канон TDD как practice (red-green-refactor), но шире — про дисциплину малых шагов и проектирование через тесты. Читать даже если не делаешь strict-TDD.
- Lisa Crispin, Janet Gregory — **[Agile Testing: A Practical Guide for Testers and Agile Teams](https://www.amazon.com/Agile-Testing-Practical-Guide-Testers/dp/0321534468)** (Addison-Wesley, 2008). **База.** Test quadrants (Brian Marick), test pyramid, whole-team approach. Уравновешивает узкий developer-testing взгляд.
- Roy Osherove — **[The Art of Unit Testing](https://www.artofunittesting.com/)** (Manning, 3rd ed. 2024). **База.** Прикладная книга по unit-testing patterns, mock / stub / spy distinction, test smells. Третье издание обновлено под современный стек.
- Vladimir Khorikov — **[Unit Testing Principles, Practices, and Patterns](https://www.manning.com/books/unit-testing)** (Manning, 2020). **База.** Schools of thought (London vs Detroit), what is unit, test value model, integration vs unit boundaries. Более глубокий заход после Osherove.

### Статьи и доклады

- Mike Cohn — **[The Forgotten Layer of the Test Automation Pyramid](https://www.mountaingoatsoftware.com/blog/the-forgotten-layer-of-the-test-automation-pyramid)** (2009). **База.** Оригинал test pyramid concept. Короткий пост, но фундамент для современного testing discourse.
- Martin Fowler — **[Test Pyramid](https://martinfowler.com/bliki/TestPyramid.html)** и **[On the Diverse And Fantastical Shapes of Testing](https://martinfowler.com/articles/2021-test-shapes.html)**. **База.** Fowler рефлексирует над pyramid 12 лет спустя, рассматривает альтернативные shapes (honeycomb, trophy) для разных систем. Полезно понимать, что pyramid — guideline, не догма.
- Google Testing Blog — **[Just Say No to More End-to-End Tests](https://testing.googleblog.com/2015/04/just-say-no-to-more-end-to-end-tests.html)** (2015). **База.** Google argument против e2e-heavy approach: dramatic flake rates, длинный feedback loop, высокая стоимость maintenance. Контекст и условия применимости.
- Martin Fowler — **[Eradicating Non-Determinism in Tests](https://martinfowler.com/articles/nonDeterminism.html)**. **База.** Канонический разбор причин flake'а (timing, shared state, external deps, test order, infrastructure) и стратегии устранения. Читать перед тем как начать quarantine'ить тесты.
- **[Contract Testing — Pact docs intro](https://docs.pact.io/getting_started/what_is_contract_testing)**. **База.** Объяснение consumer-driven contracts как класса тестов. Pact — конкретная реализация; concept универсален.
- Stryker — **[An introduction to mutation testing](https://stryker-mutator.io/docs/mutation-testing-elements/supported-mutators/)**. **База.** Mutation testing concept + practical examples; в каждом mainstream языке есть mutator. Mutation score как метрика дополняет coverage.
- Spotify Labs — **[Testing of Microservices](https://engineering.atspotify.com/2018/01/testing-of-microservices/)**. **Дополнительно.** Test honeycomb как ребаланс pyramid для microservices (упор на integration / contract вместо broad unit). Альтернативная shape под распределённую систему.
- Andrew Trenk, Adam Bender — **[Software Engineering at Google: chapter Testing Overview](https://abseil.io/resources/swe-book/html/ch11.html)** (O'Reilly, 2020). **База.** Google's testing philosophy at scale — small/medium/large test sizes (вместо unit/integration/e2e), hermetic test policy, beneficial vs harmful flakiness.
- **[Goodhart's Law](https://en.wikipedia.org/wiki/Goodhart%27s_law)** ("When a measure becomes a target, it ceases to be a good measure"). **База для понимания почему coverage as target — антипаттерн.**

## Best practices

- **Test pyramid как baseline, но не догма — выбирай shape под систему.** Антипаттерн: «у нас 80% e2e, потому что они "ближе к пользователю"» — ice cream cone, медленный feedback (часы вместо минут), хрупкость (любое UI / network glitch ломает test). Базовая pyramid (много unit → меньше integration → мало e2e) подходит большинству; для distributed systems лучше **honeycomb** (упор на integration / contract); для backend без сложной UI — **trophy** (Kent C. Dodds). Решение — обдуманный выбор под характеристики системы, не cargo cult.
- **Contract testing — обязательный слой в distributed systems, не «когда-нибудь».** Антипаттерн: «у нас unit и e2e, contract не нужен». Unit'ы проверяют изолированно, e2e — медленно и нестабильно; consumer ломается на breaking change в provider'е только когда оба деплоятся вместе (часто = постфактум, в проде). Pact / Spring Cloud Contract проверяют compatibility в CI каждой стороны независимо. Cost внедрения — час на сервис; ROI — class of integration bugs устранён.
- **Flake rate измеряется, flaky tests изолируются.** Антипаттерн: «retry помог, идём дальше». 5% flake rate = 100% trust loss в CI: developer видит red → нажимает retry, не глядя на root cause; реальный regression проходит мимо. Метрика — flake rate per test, dashboard, weekly review. Lifecycle: quarantine (не блокирует merge) → root cause analysis → fix или delete. Trunk / BuildPulse / Datadog CI Visibility делают это видимым; без tooling — слепое пятно.
- **Coverage — diagnostic, не target.** Антипаттерн: «80% coverage обязательно для merge». Goodhart's law: developer пишет тесты без assertions / тесты на trivial code (геттеры) — coverage growth, signal value не растёт. Coverage полезен как обратный сигнал (что **не** покрыто), как сравнение модулей (где coverage упал — почему?), но не как absolute target. **Mutation score** — гораздо более честная метрика качества тестов, но дороже считать (CI run × N мутаций).
- **Test data strategy — explicit decision, не «выгрузим из прода».** Антипаттерн: prod dump в staging без анонимизации (GDPR / PII fail) либо ручные fixtures в каждом тесте (drift, дублирование). Factories (FactoryBot / factory_boy / mommy_factories) дают composable test data; builder pattern в коде даёт читаемость; golden datasets для regression baseline; ephemeral DB per test (Testcontainers) — изоляция. PII / GDPR — анонимизация на границе prod → staging, не «забыли потом».
- **Tests как production code — review, ownership, refactor, deletion.** Антипаттерн: «test code не важен, как-нибудь работает». Test code maintenance скрытая стоимость поддержки сервиса (часто 30–50% test code volume). Тесты, которые ничего не ловят но дорого maintain'ить — кандидаты на deletion; тесты, которые ловят bug дважды — keep и углублять; broken tests — bug в коде или в тесте (всегда триаж, никогда `@Disabled` без followup ticket с deadline).
- **Test environment management — ephemeral per CI run, не shared staging.** Антипаттерн: один shared staging env, тесты сталкиваются (data pollution, port conflicts, race conditions). Ephemeral env per PR (Docker Compose / Testcontainers / k8s namespace per branch) даёт isolation; cost — управляемый при правильном tooling; alternative shared staging накапливает test data debt и теряет signal value. Hermetic tests (no external deps, no internet) — Google policy для large test base.

## Связанные листья

- **[CI/CD](/The-Way-of-SRE/leaves/engineering/ci-cd/)** — тесты живут и enforce'ятся в pipeline (CI ≤ 10 минут + zero flaky tests из CI/CD best practices). Без testing strategy CI green = false confidence. Это сосед под одним L1.
- **[Programming Languages](/The-Way-of-SRE/leaves/engineering/programming-languages/)** — language-specific testing tools / patterns (`go test` table-driven, `pytest` fixtures, JUnit annotations). Соседний лист под одним L1.
- **[Progressive Delivery](/The-Way-of-SRE/leaves/practices/progressive-delivery/)** — canary с health gate — это runtime test (отвечает на «прод ведёт себя ОК?»); pre-deploy tests — это compile/build/staging tests. Граница: тесты до деплоя, canary после. Без тестов до canary catches только runtime regressions, не correctness.
- **[Chaos Engineering](/The-Way-of-SRE/leaves/engineering/chaos-engineering/)** — chaos = hypothesis-driven experiments на real (или near-real) system; load / performance tests — known forcing function в staging. Дополняют, не заменяют друг друга. Chaos находит failure modes; tests verify response к known input.
- **[Resilience Patterns](/The-Way-of-SRE/leaves/engineering/resilience-patterns/)** — testability — это атрибут архитектуры: idempotency, dependency injection, side effects на границах. Resilient design ↔ testable design.
- **[SLO Engineering](/The-Way-of-SRE/leaves/engineering/slo-engineering/)** — performance / load tests генерируют baselines для SLI / SLO (что значит «нормальная latency под нагрузкой»). Без load testing SLO targets — guess.
- **[Toil Tracking](/The-Way-of-SRE/leaves/engineering/toil-tracking/)** — manual test execution = toil; automation тестов — toil reduction. Метрика «% manual regression effort» — кандидат в toil dashboard.
- **[Vulnerability Management](/The-Way-of-SRE/leaves/practices/vulnerability-management/)** — security testing (SAST / DAST / fuzzing) — отдельная категория в test portfolio; fuzzing (libFuzzer / AFL / jazzer / go-fuzz) как property-based testing для security boundary inputs.

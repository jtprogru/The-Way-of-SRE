# Как контрибутить

The Way of SRE — карта компетенций, а не сборник статей. Ценность приносит не объём текста, а точность: одна практика, названная своим именем, с честной оценкой источников и границей применимости. Поэтому PR на две строки здесь такой же нормальный вклад, как новый лист.

Обсуждение, вопросы «а куда это вешать» и «нужен ли такой лист вообще» — в [чате в Telegram](https://t.me/+BPP6mMOs34s2Yzcy). Анонсы новых листьев и изменений — в [канале](https://t.me/+LFsXS2FuZiwwMzky). Спросить до того, как писать текст, дешевле, чем переделывать после ревью.

## С чего начать

Самое полезное для проекта и самое дешёвое для контрибутора:

- **Фактические ошибки.** Битая ссылка, устаревшая версия стандарта, число, которого нет в источнике, разъехавшийся между листьями пересказ одного и того же публичного кейса.
- **Открытые вопросы.** В листьях со статусом `draft` есть секция «Открытые вопросы» и маркеры `TBD` — это прямое приглашение к PR.
- **Материалы.** Хороший источник с личной оценкой ценнее пяти ссылок без неё.
- **Новые листья.** Самое трудоёмкое. Сначала стоит сверить идею с [Методологией](https://jtprogru.github.io/The-Way-of-SRE/methodology/) и обсудить в [чате](https://t.me/+BPP6mMOs34s2Yzcy): чаще всего предложенная практика уже описана в карте под другим именем.

## Что где лежит

| Путь | За что отвечает |
| ---- | --------------- |
| `src/data/roadmap.ts` | источник правды по структуре: ветви, L1, листья, приоритеты |
| `src/content/docs/<branch>/<slug>.md` | содержимое листа (`.md`), рядом с hub-страницами L1 (`.mdx`) |
| `inventory/leaf-template.md` | шаблон листа |
| `src/content/docs/<branch>/<l1-id>.mdx` | страница L1: описание прозой, L2 и практики из данных |
| `src/content/docs/glossary.mdx` | глоссарий, единое место истины по терминам |
| `inventory/style-guide.md` | голос, структура секций, запрещённые паттерны, чеклист готовности |
| `inventory/terminology.md` | как переводить термины: четыре категории и правила графики |
| `inventory/overlaps.md` | решения по пересечениям между ветвями |
| `tools/style/` | механическая часть чеклиста, `make style` |
| `tools/cover/` | генератор обложки README |
| `logo/cover-*.svg` | сгенерированные файлы, руками не правятся |

Навигация, сайдбар, mind map, страницы ветвей и приоритеты рендерятся из `roadmap.ts`. Ни `astro.config.mjs`, ни сайдбар руками править не нужно — добавленный в данные лист появляется во всех четырёх местах сам.

## Локальный запуск

Нужны [bun](https://bun.sh) (в CI закреплена версия 1.3.14) и `python3` для стиль-чека — сторонних Python-пакетов нет, только стандартная библиотека.

```bash
make          # список целей
make dev      # dev-сервер на http://localhost:4321/The-Way-of-SRE/
make check    # ровно то, что гоняет CI на PR
```

Зависимости ставятся сами при первом запуске любой цели. `make check` локально и проверка в PR — одна и та же команда, разойтись им негде: зелёный прогон локально означает зелёный CI.

## Рабочий процесс

1. Ветка от `main`: `docs/<что>`, `feat/<что>`, `fix/<что>`. Прямо в `main` не коммитим.
2. Атомарные коммиты — одно логическое изменение на коммит. Правка листа и рефакторинг данных живут в разных коммитах.
3. Сообщение коммита по [Conventional Commits](https://www.conventionalcommits.org/): тип и scope на английском, тема — по-русски, как в истории репозитория (`docs(leaves): переписать Runbooks под шаблон`).
4. `make check` перед пушем.
5. PR по [шаблону](.github/PULL_REQUEST_TEMPLATE.md). Чеклист листа в нём — не формальность: по нему идёт ревью.
6. Мерж после зелёного CI.

## Как добавить новый лист

Лист — это конкретная практика внутри домена, а не сам домен. `Incident Management` — это L1, а `Blameless Postmortem` — лист. Если название листа совпадает с названием L1, скорее всего описывается домен целиком, и его нужно резать.

**1. Выбрать точку подключения.** Самостоятельная практика раздела вешается под L1. Уточнение уже написанной практики — в её поле `children` (`Runbooks → Playbooks`). Уровень вложенности ровно один: под подлистом детей быть не может, и попытка их завести не пройдёт `make typecheck`. Подлист живёт в той же ветви, что и родитель, приоритет у него собственный.

**2. Создать файл из шаблона.**

```bash
cp inventory/leaf-template.md src/content/docs/engineering/<slug>.md
```

Ветвь — `culture`, `engineering` или `practices`. Slug латиницей через дефис, совпадает с последним сегментом URL.

**3. Заполнить frontmatter.** `title` — имя компетенции, `description` — одна фраза не длиннее 200 символов, не пересказ листа. Двоеточие в `description` без кавычек ломает парсер — известный YAML gotcha, `make check` его поймает. Плюс два поля листа: `sfia` — уровни, для которых расписаны умения, и `status` на пути `draft → review → stable`. Ветвь, путь и приоритет во frontmatter не пишутся: они приходят из `roadmap.ts` и рендерятся под заголовком сами.

**4. Написать содержимое** по структуре шаблона: lead-параграф с мнением или диагнозом (не пересказ `description`), «Что должен уметь» с привязкой к SFIA-уровням, «Материалы» с личной оценкой минимум для половины источников, «Best practices», «Связанные листья» с типом связи, «Открытые вопросы» для черновиков.

**5. Зарегистрировать лист в `src/data/roadmap.ts`** под нужным L1:

```ts
{
  id: 'sli-based-alerting',
  label: 'SLI-based Alerting',
  href: '/engineering/sli-based-alerting/',
  priority: 'must',
},
```

`id` совпадает со slug файла, `href` — плоский путь `/<branch>/<slug>/` независимо от вложенности; slug не должен совпадать с id какого-нибудь L1 этой ветви, они делят одно пространство имён. Приоритет — один из `must`, `mandatory`, `nice`, `ondemand`; что они значат, описано в [Методологии](https://jtprogru.github.io/The-Way-of-SRE/methodology/).

И назвать компетенцию в инвентаре `l2` того же L1 — там она встанет ссылкой на новый лист. Если такого концепта в инвентаре ещё не было, он добавляется в осмысленное по смыслу место списка, а не в конец. `make data-check` не пропустит лист, которого нет в `l2`.

**6. Добавить новые термины в глоссарий.** Если термин встречается в листе и его нет в `glossary.mdx` — он добавляется тем же PR или отдельным follow-up, с категорией по `inventory/terminology.md`.

**7. Прогнать проверки.**

```bash
make style LEAF=src/content/docs/engineering/<slug>.md
make check
```

## Как править существующий лист

Один PR — одно атомарное изменение в одном файле. Отдельно стоит помнить про две вещи.

**Ссылки и числа проверяются открыванием.** Не «ссылка не 404», а «под этим названием лежит этот материал этого автора». Датируемое утверждение — дата инцидента, число пострадавших, редакция стандарта — подтверждается первичным источником: постмортемом самой компании, статьёй автора, текстом спецификации. Пересказ в чужом блоге источником не считается. Скрипт это не ловит, это остаётся за человеком.

**Slug — часть контракта.** Меняешь `slug` — обновляешь входящие ссылки в других листьях и `href` в `roadmap.ts` тем же PR.

## Как менять структуру карты

Изменения на уровне ветвей и L1 — редкая и дорогая операция, они затрагивают всю навигацию. Такой PR сверяется с [Методологией](https://jtprogru.github.io/The-Way-of-SRE/methodology/) и `inventory/overlaps.md`, а мотивацию имеет смысл обсудить в чате заранее.

Инвариант: у каждого L1 из `roadmap.ts` должна быть страница `src/content/docs/<branch>/<l1-id>.mdx`. Новый L1 — это запись в данных плюс страница, обязательно в одном PR, иначе карточка на странице ветви ведёт в никуда.

### Почему hub-страницы — файлы, а не генерация

Все 24 hub-страницы устроены одинаково и занимают по 15 строк, так что мысль сгенерировать их из данных приходит быстро. Решено оставить файлами. Шаблонных строк там шесть — два импорта, `<L2Concepts>`, заголовок `## Практики` и `<NodeCards>`; остальное — фронт-маттер и абзац про домен, а он у каждого L1 свой и пишется руками.

Свернуть хвост в override `MarkdownContent.astro` по флагу `hub: true` технически проще всего, но заголовок `## Практики` тогда рисует компонент, а оглавление страницы Starlight собирает из markdown-заголовков. Заголовок пропадёт из правой колонки, и файл перестанет честно показывать, что на странице.

Если генерация когда-нибудь понадобится, дешёвый путь — кодогенерация самих `.mdx` по образцу `make cover`: абзац про домен переезжает в `roadmap.ts` отдельным полем, цель Makefile раскладывает файлы, режим `--check` ловит расхождение данных с файлами в `make check`. Облик страниц при этом не меняется вообще: на выходе тот же файл, что лежит сейчас. Дорогой путь — свой loader поверх `docsLoader()` от Starlight: синтетическая запись коллекции обязана нести готовый HTML, а тело хаба состоит из двух Astro-компонентов, которые loader не рендерит. За эту цену покупается ровно то же, что за первую.

## Что генерируется, а не пишется

| Что | Чем обновляется |
| --- | --------------- |
| оглавление `README.md` | `make toc` |
| обложка `logo/cover-*.svg` | `make cover` |
| сайдбар, mind map, страницы ветвей, приоритеты | ничем, рендерятся из `roadmap.ts` на билде |

Оглавление и обложка коммитятся в репозиторий, поэтому `make check` их не перерисовывает, а сверяет: цель падает ровно в тот момент, когда данные ушли вперёд файла.

## Проверки

`make check` — это оглавление README, обложка, линт markdown, типы, сборка сайта и стиль-чек листьев.

Стиль-чек (`tools/style/`) проверяет механическую часть чеклиста из `inventory/style-guide.md`: голос автора и его распределение по секциям, долю шаблонных блоков в Best practices, дублирование `description` в первом абзаце, падежные гибриды через дефис, кальки, долю источников с личной оценкой, ритм фраз. В CI блокируют только детерминированные правила §3.1–§3.8 уровня `!`. Наблюдения уровня `~` сборку не роняют — это повод посмотреть, а не обязательство переписать.

Чего скрипт не умеет: отличить пример из практики от синтетического и проверить, что источник существует и говорит то, что ему приписано. Это ревью.

## Голос

Полные правила — в `inventory/style-guide.md`, здесь короткая выжимка того, из-за чего чаще всего приходится переписывать.

Текст пишется от первого лица как наблюдение профессионала: «я регулярно вижу», «по моим наблюдениям, чаще выбирают X». Не «команды должны» и не «я бы выбрал». В каждом листе обязательны один конкретный пример (публичный incident или авторское наблюдение), одно явное мнение и одна граница применимости — без них лист неотличим от сгенерированного.

Устоявшиеся англицизмы (SLI/SLO, postmortem, runbook, on-call, blameless) пишутся латиницей курсивом без склонения. Явные кальки переводятся. Падежные гибриды через дефис («mitigation-фазы», «high-severity incident») запрещены; сложения с аббревиатурой и термином («SFIA-уровни», «unit-тесты») — нормальны.

Абзацы в markdown не переносятся руками по ширине: один абзац — одна строка, перенос делает рендерер.

# Шаблон: Процедура отката

Процедура отката записывает для одного сервиса, по какому условию релиз откатывают, кто это решает и какими действиями. Её пишут и проверяют до выкатки, а не в момент инцидента. Почему откат должен быть проще наката исправления и как он связан с канарейкой и feature flag, разобрано в листе [Progressive Delivery](https://jtprogru.github.io/The-Way-of-SRE/practices/progressive-delivery/).

## Когда применять

- Сервис выкатывается регулярно, а откат каждый раз вспоминают по памяти.
- Откат состоит не из одной команды: кроме кода есть флаги, конфигурация, миграции схемы.
- Готовится рискованное изменение, и план отката нужен до деплоя.

## Когда не применять

- Нужна реакция на конкретный алерт. Это [runbook](runbook.md), а процедура отката в нём один из вариантов митигации.
- Изменение необратимо: удалённые данные, односторонняя миграция. Процедура отката здесь даст ложное спокойствие, нужен план восстановления.
- Инцидент требует координации нескольких команд. Это [playbook](https://jtprogru.github.io/The-Way-of-SRE/culture/playbooks/).

## Как заполнять

- Текст в квадратных скобках — подсказка. Его нужно заменить своим или удалить.
- Условия отката записывай числами: порог и длительность. «Если что-то пошло не так» условием не считается.
- Проверь откат до того, как он понадобится: на стенде или на учениях. Дата последней проверки обязательна.
- Раздел «Что откат не возвращает» заполняй первым. Данные, записанные новой версией, и кэши на клиентах команда `undo` не трогает.
- Миграция схемы и изменение кода в одном деплое делают откат опасным для данных. Если сервис так выкатывается, это записывается в таблицу явно.
- Команды копируются как есть. Команды в шаблоне — пример на Kubernetes.

Сам документ начинается ниже линии. Копировать нужно только его.

- **Сервис:** [название и ссылка на репозиторий или карточку сервиса]
- **Владелец:** [одна роль или одна команда]
- **Способ выкатки:** [rolling update / canary / blue-green / через feature flag]
- **Последняя проверка отката:** [YYYY-MM-DD; как проверяли: учения, откат в инциденте, прогон на стенде]
- **Следующий пересмотр:** [YYYY-MM-DD]

## Когда откатывать

Условия, при которых откат запускают без обсуждения.

- [Доля ошибок выше X% дольше Y минут после выкатки]
- [p99 latency выше Z мс дольше Y минут после выкатки]
- [Сработал алерт на burn rate: ссылка на алерт]
- [Новая версия не проходит health check]

**Автоматический откат:** [есть или нет; по какому условию срабатывает и где настроен]

## Кто решает

- **В рабочем порядке:** [роль, например тот, кто выкатывал]
- **Во время инцидента:** [роль, например incident commander]
- **Кого уведомить и где:** [роли и канал]

## Шаги

1. Сообщить о решении: [где и что написать: что откатываем, с какой версии на какую и почему]

2. Откатить на предыдущую версию.

   ```bash
   kubectl rollout undo deployment/api-server -n production
   ```

   Если нужна не предыдущая версия, а конкретная, номер ревизии берётся из истории:

   ```bash
   kubectl rollout history deployment/api-server -n production
   kubectl rollout undo deployment/api-server -n production --to-revision=42
   ```

3. Дождаться завершения.

   ```bash
   kubectl rollout status deployment/api-server -n production
   ```

4. [Остальные действия из таблицы выше: флаг, конфигурация, обратная миграция]
